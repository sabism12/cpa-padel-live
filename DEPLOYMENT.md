# Deploy CPA Padel to Render

This project runs as one Node/Express web service. React/Vite builds the website; the same Express process serves the website, tournament APIs, admin APIs, and Server-Sent Events (SSE) used by live viewers.

## 1. Prepare a private GitHub repository

1. Sign in to GitHub and choose **New repository**.
2. Give it a name such as `cpa-padel-tournament` and choose **Private**.
3. Do not upload `.env`, `.env.local`, passwords, or other secret files. `.gitignore` excludes those files, `node_modules`, build output, and the runtime `data/` directory.
4. In the project folder, check `git remote -v`. This copied workspace may still have the original repository configured as `origin`. Change the copied workspace's remote to the new private repository before pushing; for example:

   ```bash
   git remote set-url origin git@github.com:YOUR_GITHUB_NAME/cpa-padel-tournament.git
   git push -u origin main
   ```

   Replace `YOUR_GITHUB_NAME` with your GitHub username. This changes only this copy's Git configuration. Do not push to the original repository.

The ignored `data/tournament_state.json` is generated from the existing seed data if no saved state exists. For production, the live file belongs on the Render persistent disk described below, not in Git.

**One-time state transfer note:** a new Render disk starts empty, so it is seeded
with the existing CPA roster but does not automatically copy a local ignored
`data/tournament_state.json` (including local scores, settings, or draw
progress). Do not commit that file because it contains private tournament and
admin data. If those local results must be preserved on the first Render
deployment, pause before the first service start and arrange a secure one-time
copy to the persistent disk. After state exists on that disk, ordinary deploys
and restarts preserve it automatically.

## 2. Create the Render service

This repository includes `render.yaml`:

- Runtime: Node
- Build command: `npm ci && npm run build`
- Start command: `npm start`
- `npm start` sets production mode and launches the compiled `dist/server.cjs`
- `NODE_ENV=production`
- One web-service instance
- Health check: `GET /health`
- A 1 GB persistent disk mounted at `/var/data`
- `DATA_DIR=/var/data`
- A private `SESSION_SECRET` generated by Render
- `INITIAL_ADMIN_PASSWORD` entered privately during Blueprint setup; used only when a new production state file is seeded

In the Render Dashboard:

1. Select **New** → **Blueprint**.
2. Connect the private GitHub repository.
3. Review the service and persistent disk in `render.yaml` and confirm creation. The Starter web-service plan is paid; Render persistent disks are not available on its free web-service plan.
4. Wait for the first build and deploy to finish. `/health` should return `{"status":"ok"}`.
5. Open the Render service URL. The existing site is `/`, the public draw is `/draw`, and the protected draw controls are `/draw/admin`.

If you create the web service manually instead of using the Blueprint, set:

| Setting | Value |
| --- | --- |
| Build command | `npm ci && npm run build` |
| Start command | `npm start` |
| `NODE_ENV` | `production` |
| `DATA_DIR` | `/var/data` |
| `SESSION_SECRET` | A private random string of at least 32 characters |
| `INITIAL_ADMIN_PASSWORD` | Set privately before the first start on a new disk |

Attach a 1 GB persistent disk at **`/var/data`**. The app writes its state to `$DATA_DIR/tournament_state.json` (therefore `/var/data/tournament_state.json` on Render). `/var/data` is Render's persistent data directory; the app's default local `./data` directory remains unchanged for local development.

The disk is essential: Render's application filesystem is temporary. Without the disk, tournament scores, admin settings, and draw results may disappear when the service is replaced. Keep the same disk attached during later deploys. The server creates the directory and initial JSON file when starting for the first time. Existing valid state is loaded on restart; malformed state causes startup to fail rather than silently replacing the saved tournament.

## 3. Secrets and administrator access

- Keep `SESSION_SECRET` private. The Blueprint generates it; do not prefix it with `VITE_` or put it in frontend code.
- Enter `INITIAL_ADMIN_PASSWORD` privately when Render prompts for it. It is used only if `/var/data/tournament_state.json` does not already exist; public APIs never return it.
- Do not commit any `.env` file. `SESSION_SECRET` is only needed on the server.
- The administrator password is stored in tournament settings on the persistent disk, not in the Render Blueprint. An existing disk keeps its existing password across deploys.
- The historical local first-run default was `admin123`; never use it for the real tournament. Production refuses to seed a new state until `INITIAL_ADMIN_PASSWORD` is provided. Confirm/change the saved password at `/admin` → **Rules & Scoring** → **Administrator Password** before the event. Saving settings persists the change to the disk.
- An existing valid state file keeps its existing administrator password. Redeploying or changing `INITIAL_ADMIN_PASSWORD` does not overwrite a saved tournament or change its password.

`CORS_ORIGINS` is optional. Same-origin website requests need no CORS setting. If a trusted external browser tool must call this service cross-origin, set `CORS_ORIGINS` to a comma-separated allowlist of exact origins, for example `https://tool.example`. Do not use `*` for a production allowlist.

## 4. One service instance

Keep the Render service at **one instance**. The tournament state is held in one Node process and saved to one local file; running multiple instances would give them separate in-memory states and separate SSE subscriber lists. Do not enable autoscaling or multiple workers unless the state/realtime design is first migrated to shared storage.

One instance is suitable for the requested ~100 spectators: viewers use one lightweight SSE connection each, heartbeat comments keep quiet connections alive, and the browser fetches snapshots on initial load/reconnect. A 15-second poll is only used as a fallback while SSE is disconnected.

## 5. Test the deployed site

1. Visit `/` and verify the existing tournament site loads.
2. Visit `/draw` in a logged-out/private browser window. Spectators should not need to sign in.
3. Visit `/draw/admin` and sign in with the tournament administrator account.
4. Initialize or continue a test draw and verify `/draw` updates without a refresh.
5. Refresh the spectator page and confirm it restores the current progress and group assignments.
6. Test Undo and Reset only on a test draw; Reset clears draw results but keeps pairs.
7. After a draw update, restart the Render service and verify the same draw state returns from the persistent disk.
8. Confirm `/health` returns `{"status":"ok"}`.

## Troubleshooting

- **Service fails to start:** Open Render → service → **Logs**. Confirm `npm start`, `NODE_ENV=production`, Render's `PORT`, a `SESSION_SECRET` with at least 32 characters, and `INITIAL_ADMIN_PASSWORD` if starting on an empty disk.
- **Port/binding error:** Do not configure a fixed port. The server listens on Render's `PORT` and binds to `0.0.0.0`.
- **Tournament state resets or is missing:** Confirm the disk is attached at `/var/data` and `DATA_DIR` is `/var/data`. Check service logs for write errors. Do not remove/recreate the disk.
- **State file is reported invalid:** Keep a copy of the disk/file and inspect it before replacing anything. The app intentionally refuses to overwrite an existing malformed state file with demo data.
- **SSE does not update:** Confirm `/api/live-events` is reachable through the same Render URL. EventSource reconnects automatically; viewers also fetch a fresh state on reconnect and poll every 15 seconds as a fallback.
- **Admin login fails:** Check the password saved in persistent tournament settings. Deploying new code does not replace settings already on the disk.
- **Assets do not load:** Use the Render service root URL and its `/draw` routes; do not configure a subpath or localhost URL. Check the deployment build log for successful Vite output.
- **Cross-origin integration fails:** Add its exact origin to `CORS_ORIGINS`. The CPA website itself is same-origin and does not require CORS.

## Local production commands

From the project folder run:

```bash
npm install
npm run build
npm start
```

`npm start` sets `NODE_ENV=production` and launches the compiled server. For a
local production test, set a private `SESSION_SECRET` (32+ characters), set
`INITIAL_ADMIN_PASSWORD` if using a new/empty data directory, and optionally set
`PORT`/`DATA_DIR`. Without `DATA_DIR`, the app uses `./data`. `npm run dev`
continues to run the existing local development server.
